# Suances - Sistema de Gestión Integral para Restaurantes

## 📋 Descripción del Proyecto

Suances es un **SaaS (Software as a Service) de gestión integral para restaurantes** diseñado con arquitectura de microservicios. El sistema permite controlar todas las operaciones de un restaurante de manera integrada, desde la gestión de mesas y comandas hasta el control de stock y rentabilidad.

### Objetivos del Sistema

- **Control de stock real**: Seguimiento automático del inventario basado en consumo
- **Costes reales**: Cálculo dinámico del coste de cada plato basado en ingredientes
- **Medición de rentabilidad**: Análisis de márgenes por plato, turno y período
- **Coordinación sala-caja**: Flujo seamless entre atención al cliente y facturación
- **Automatización de alertas**: Notificaciones cuando el stock baja de umbrales
- **Escalabilidad**: Arquitectura preparada para multi-local en el futuro

## 🏗️ Arquitectura del Sistema

### Enfoque: Microservicios

El sistema está dividido en **microservicios independientes**, cada uno con su propia responsabilidad de negocio. Esta arquitectura permite:

- Despliegue independiente de cada módulo
- Escalabilidad individual por servicio
- Aislamiento de fallos
- Tecnología optimizada por caso de uso

## 📦 Microservicios del Backend

### 1. SALA Service (`rest-sala-service`)

**Puerto**: Por configurar (típico: 8081)
**Descripción**: Gestión operativa diaria del restaurante

**Responsabilidades**:
- Gestión de salas (configuración de planos)
- Gestión de mesas y estados operativos
- Comandas y seguimiento de pedidos
- Flujo de platos por rondas (entrantes, primeros, segundos, постres)
- Control de estado del servicio

**Entidades principales**:
- Sala
- Mesa
- Comanda
- ItemComanda

**Eventos publicados**:
- `comanda.abierta`
- `plato.pedido`
- `plato.enviado.cocina`
- `plato.servido`

---

### 2. CARTA Service (`rest-carta-service`)

**Puerto**: Por configurar (típico: 8082)
**Descripción**: Núcleo económico y de gestión de producto

**Responsabilidades**:
- Catálogo de ingredientes y distribuidores
- Gestión de stock de ingredientes
- Escandallos (fichas técnicas de platos)
- Platos y menús
- Tipos de carta por horario
- Cálculo de coste real de platos
- Alertas de stock mínimo

**Entidades principales**:
- Ingrediente
- Distribuidor
- Plato
- Escandallo
- TipoCarta

**Eventos consumidos**:
- `sala.plato.pedido` → Descuenta stock, incrementa contador
- `sala.comanda.cerrada` → Regenerar estadísticas

**Eventos publicados**:
- `ingrediente.stock.bajo` (alerta)
- `plato.coste.actualizado`

### 4. CAJA Service

**Descripción**: Gestión económica diaria

**Responsabilidades**:

**Eventos publicados**:

### 5. PERSONAL Service (`rest-personal-service`)

**Puerto**: Por configurar (típico: 8084)
**Descripción**: Seguridad y gestión de usuarios

**Responsabilidades**:
- Gestión de usuarios del sistema
- Roles y permisos:
  - **OWNER** (Propietario): Acceso total
  - **MANAGER** (Gerente): Gestión operativa
  - **WAITER** (Camarero**: Operación básica
- Firma de tokens JWT
- Validación de autenticación

**Entidades principales**:
- Usuario
- Rol

**Roles del sistema**:
```
OWNER    → Acceso total: config, reportes, finanzas
MANAGER  → Gestión: mesas, cartas, personal, reportes
WAITER   → Operación: comandas, pedidos, reservas
```

## 🔄 Comunicación entre Microservicios

### Patrón: Event-Driven Architecture

#### REST (Operaciones Síncronas)
- Consultas directas entre servicios
- Operaciones administrativas
- Creación/actualización de recursos
- Comunicación punto a punto

**Ejemplos**:
- Frontend → Sala: "Crear comanda"
- Frontend → Carta: "Obtener menú del día"
- Frontend → Personal: "Login"

#### Redis Streams (Eventos Asíncronos)
- Eventos de negocio que requieren múltiples reaccionadores
- Desacoplamiento fuerte entre servicios
- Garantía de procesamiento
- Idempotencia

**Eventos del sistema**:

| Evento | Productor | Consumi­dores | Descripción |
|--------|-----------|---------------|-------------|
| `sala.comanda.abierta` | Sala | Carta, Reservas | Nueva comanda iniciada |
| `sala.plato.pedido` | Sala | Carta, Caja | Plato añadido a comanda |
| `sala.plato.enviado` | Sala | Carta | Plato enviado a cocina |
| `sala.plato.servido` | Sala | Carta | Plato servido al cliente |
| `sala.comanda.cerrada` | Sala | Carta, Caja | Comanda finalizada |
| `carta.ingrediente.stock.bajo` | Carta | (Alertas) | Stock mínimo alcanzado |
| `caja.ticket.pagado` | Caja | Sala | Ticketcobrado |

## 🔐 Seguridad

### Autenticación y Autorización

```
┌──────────────┐     JWT Firmado      ┌──────────────────┐
│   CLIENTE   │ ─────────────────►  │   MICROSERVICIO  │
│  (Frontend) │    Authorization:    │    (Validación)  │
│             │    Bearer <token>    │                  │
└──────────────┘                      └──────────────────┘
       │                                      │
       │                                      ▼
       │                              ┌──────────────────┐
       │                              │  PERSONAL Service │
       │                              │  (Firma/Validación)│
       │                              └──────────────────┘
       │                                     │
       ▼                                     ▼
┌──────────────┐                      ┌──────────────────┐
│    LOGIN     │◄─────────────────────│  JWT Generation  │
│  (Credenciales)                     │  (Usuario + Rol) │
└──────────────┘                      └──────────────────┘
```

### Flujo de Seguridad

1. **Login**: Cliente envía credenciales a Personal Service
2. **Firma**: Personal Service genera JWT con:
   - `sub`: userId
   - `name`: nombre del usuario
   - `role`: rol del usuario (OWNER, MANAGER, WAITER)
3. **Token**: Cliente incluye JWT en header `Authorization: Bearer <token>`
4. **Validación**: Cada microservicio valida:
   - Firma del token (secret compartido)
   - Expiración
   - Permisos (Spring Security `@PreAuthorize`)

### Configuración de Seguridad

```java
// Ejemplo de protección por rol
@PreAuthorize("hasAnyRole('OWNER','MANAGER','WAITER')")
public ComandaResponse crear(@Valid @RequestBody ComandaRequest request)

@PreAuthorize("hasAnyRole('OWNER','MANAGER')")  // Waiter no puede eliminar
public ResponseEntity<Void> cancelar(@PathVariable UUID id)
```

## 🔀 Flujos Principales del Sistema

### Flujo 1: Apertura de Comanda

```
1. Camarero selecciona mesa → Frontend → Sala Service
2. Sala verifica mesa disponible (sin comanda activa)
3. Sala crea Comanda con estado ABIERTA
4. Sala actualiza estado mesa → OCUPADA
5. Sala publica evento Redis: comanda.abierta
6. Carta consume evento → Prepara seguimiento de stock
7. Frontend recibe respuesta con ID de comanda
```

### Flujo 2: Pedido de Plato

```
1. Camarero añade plato(s) a la comanda
2. Sala Service:
   - Crea ItemComanda para cada plato
   - Asigna numeroRonda y tipoRonda
   - Calcula subtotal
3. Sala publica evento: plato.pedido
4. Carta consume evento:
   - Descuenta ingredientes del stock
   - Incrementa contador de veces pedido
   - Verifica umbrales → emite alerta si bajo mínimo
5. Caja consume evento → Prepara línea de ticket
6. Frontend actualiza vista de comanda
```

### Flujo 3: Envío a Cocina

```
1. Jefe de cocina/Bar solicita envío de ronda
2. Sala Service:
   - Cambia estado items → EN_PREPARACION
   - Registra horaEnvioCocina
   - Avanza estado comanda → EN_PREPARACION
3. Sala publica evento: plato.enviado.cocina
4. Carta consume evento → Actualiza disponibilidad (si es necesario)
```

### Flujo 4: Servicio del Plato

```
1. Cocinero marca plato como "listo"
2. Camarero marca como "servido"
3. Sala Service:
   - Actualiza estado → SERVIDO
   - Registra horaServido
4. Sala publica evento: plato.servido
5. Carta consume evento → Actualiza estadísticas
```

### Flujo 5: Cierre de Comanda y Pago

```
1. Camarero solicita cuenta
2. Sala:
   - Cambia estado → CUENTA
   - Calcula total con descuentos
   - Genera detalle deitems
3. Sala publica evento: comanda.cuenta.solicitada
4. Caja consume evento → Genera ticket
5. Cliente paga
6. Caja:
   - Registra método de pago
   - Cambia estado → COBRADA
   - Registra fechaCierre
7. Caja publica evento: ticket.pagado
8. Sala consume evento:
   - Cambia estado comanda → COBRADA
   - Libera mesa → DISPONIBLE
9. Carta consume evento → Regenera informes de consumo
```

## 📝 Convenciones de Código

### Estructura de Paquetes
```
com.suances.[servicio]
├── controller    # REST endpoints
├── service       # Lógica de negocio
├── repository    # Acceso a datos (JPA)
├── domain        # Entidades y value objects
│   ├── model     # JPA Entities
│   ├── dto       # Data Transfer Objects
│   └── enums     # Enumeraciones
├── event         # Productores/consumidores de eventos
├── exception     # Excepciones personalizadas
└── config        # Configuración de Spring
```

### Nomenclatura
- **Clases**: PascalCase (`ComandaController`, `ComandaService`)
- **Métodos**: camelCase (`crearComanda`, `obtenerComanda`)
- **DTOs**: Postfix `Request` o `Response` (`ComandaRequest`, `ComandaResponse`)
- **Entidades**: Nombre del dominio en singular (`Comanda`, `Mesa`)
- **Tablas BD**: Plural (`comandas`, `mesas`)
- **Variables**: camelCase, nombres descriptivos
